0. 一句话结论

这个魔改包里有 三套彼此独立 的"更新/升级"通道并行工作，前两轮各只打掉一套，所以弹窗一直在。
本轮把 全部 4 个注入钩子 + 字节官方升级链路 一次性清干净，并在真机验证通过。

1.1 通道 C 的反编译实证

  • 它挂在基类 Activity 的 onStart 上 → 主界面、设置页、任何页面都会触发；
  • 请求走的不是 HTTP 而是裸 TCP socket（com/iI → InetAddress.getByName("oneseeker.top") + 随机端口），所以按 URL 扫描根本扫不到；
  • 网络不可达时会回落到本地缓存继续弹（弹窗日期/版本号是当天抓到的数据）。

2. 定位过程与关键证据（为什么前两轮没打中）

轮次做法结果
第 1 轮只按"官方升级链路"思路补 17 处（NsUpdateServiceImpl / UpdateManager / com.ss.android.update）弹窗照旧 —— 因为弹窗来自魔改注入，与官方 SDK 无关
第 2 轮全 APK 扫非官方域名，找到 remote.oneseeker.top/appUpdate + libseccore.so + 34 个伪 org.checkerframework 类 → 摘掉 2 个注入钩子弹窗照旧 —— 因为通道 C 独立存在
第 3 轮（本轮）接入 ADB 真机取证 + 类集合差集 + 宿主侧引用扫描挖出 AbsActivity.onStart→com.o.Call，并实测验证通过

本轮关键证据

  1. 设备取证：/data/app/.../base.apk 的 MD5 = 545a3f54… ⇔ 与本地成品完全一致（276,684,359 B）→ 排除"你装的不是我那份"。
  2. UI dump：弹窗是标准 AlertDialog（android:id/alertTitle / message / button1），标题「温馨提示」、按钮「>>立即更新<<」；而按钮文案在 APK 里根本不存在 → 服务端/缓存下发。
  3. 窗口属主：Window{… com.phoenix.read/com.dragon.read.pages.main.MainFragmentActivity}，mOwnerUid=10260、同进程 Session → 是 App 自己弹的，不是悬浮窗/其它 App。
  4. 类集合差集：外层（魔改 24 dex）比内嵌 assets/base.apk（原始 22 dex）多 1228 个类、少 0 个 → 精确定位魔改载荷。
  5. 引用扫描：classes22 里只有 1 个宿主类引用魔改载荷 → AbsActivity → Lcom/o;。
  6. 排除 VPN：设备上跑着 Clash Meta（tun0），但其 VPN 白名单不含 uid 10260，红果走直连 → 排除"代理注入"。
  7. 排除模改服务器：DoH 实测 oneseeker.top → 154.12.86.179，55 秒采样里 App 只连 443/9443/10019，从未连它 → 弹窗走的是本地缓存（更说明必须从代码层摘钩子，而不是靠断网）。

4. 工艺与一个必须知道的坑

4.1 /sdcard 是大小写不敏感文件系统

实测：在工作区 /storage/emulated/0/... 下同时创建 CaseTest.txt 与 casetest.txt → 合并成 1 个文件。
而魔改载荷里有大量 Lcom/aA; 与 Lcom/aa;、Lcom/o; 与 Lcom/O; 这类仅大小写不同的类 →
在 /sdcard 上反编译会互相覆盖、静默丢类。

解决：本轮所有反编译 / 回编译全部改在 Termux HOME（/data/data/com.dsharnessmobile.shell/files/home，ext4，大小写敏感） 下进行，并逐个 dex 做类集合校验。

C. 用 MT管理器 装为什么会失败
MT管理器 走的是标准 PackageInstaller，没有"允许降级"能力，所以从 7.3.7.33 往 7.3.6 装必然报
「系统已存在较新版本，此安装程式套件无法安装」。
先在 MT管理器里卸载旧版再装即可（同样会清数据）；或者干脆用上面的 B。

D. 装完自检

! 测试陷阱（我踩过）：uiautomator dump 抓的是当前最前台窗口。
如果 App 不在前台（比如你正在看聊天界面），dump 出来的是别的 App，
而聊天内容里若出现 "会员纯净 / alertTitle" 等字样就会误报成弹窗。
必须先 dumpsys window | grep mCurrentFocus 确认前台是 com.phoenix.read 再 dump。

11. 【自查修正】版本号盖章策略 —— 修掉我自己的打包缺陷

11.1 我错在哪

前几轮我直接沿用了原包的 versionCode（7.3.6=73632、7.3.7.32=73732、7.3.7.33=73733）就打了包。
后果是我一开始就该预料到的：我自己的包之间互相安装也会撞降级墙 ——
在 7.3.7.33 上装 7.3.6 必然报
INSTALL_FAILED_VERSION_DOWNGRADE: Update version code 73632 is older than current 73733，
逼得你只能卸载（清数据）再装。这是打包策略问题，不是 Android 的限制。

11.2 修正方案：统一盖 high 且相同的 versionCode

项值
改法改写 AndroidManifest.xml（binary AXML）里 <manifest> 的 versionCode
盖章值100000000（三个包完全相同）
为什么相同Android 只在 新 < 旧 时才判降级；相等 = 普通覆盖，所以任何一个都能覆盖另一个，双向自由切换
为什么这么高远高于任何官方版本号 → 用 MT管理器/系统安装器装也不会被判"较新版本已存在"；同时也让 App 自认为比官方新，天然压住官方升级判断
附带好处versionName 不动（安装器仍显示 7.3.6.32 / 7.3.7.33），用户看到的版本没错乱

工具包已固化：patch_kit.sh 第 8 步自动盖章（可用 STAMP=xxx sh patch_kit.sh ... 覆盖）。

16. V5 回归 → v6 修复；以及「多出来的 read 安装包」真相

16.1 V5 暴露的问题：弹窗有两个独立来源

V5（保留模块、只摘 com.o.Call）装到真机后弹窗又出现了（截图可见「立即更新」按钮）。
原因：V5 为保住模块，把 MainFragmentActivity.onStart() → а.A(..., "…/appUpdate", …) 保留了，
而 SecCore 模块自己也会弹窗（а 本身就是 DialogFragment）。

⇒ 弹窗有两条互不依赖的路径：

  1. AbsActivity.onStart() → com.o / com.q .Call(Activity)（纯 Java 更新器）
  2. MainFragmentActivity.onStart() → а.A(...)（SecCore 原生模块）

我上一轮只证明了第 1 条会弹，漏了第 2 条 —— 这就是 V5 回归的原因。

16.2 v6 的解法：保留模块加载，掐掉它的数据源

不能删 а.A(...)：删了 → а 类不加载 → SafeLoader 不执行 → libseccore.so 不加载 → 整块模块失效（这正是第 15 节的怀疑点）。

所以 v6 改成：保留这条调用，只把参数里的更新 URL 换成打不通的死地址：

  • 模块照旧加载（原生库由类加载触发 JNI_OnLoad）；
  • 但它拿不到更新数据 → 不弹窗；
  • 同时仍摘掉 Java 侧的 com.o / com.q.Call 触发并把该方法置空。

v6 补丁集：17 处官方升级补丁 + 摘除 Call(Activity) 钩子并置空 + а.A 的 URL 改死地址 + assertIllegalAccess 置空；载荷与其余 3 个钩子全部原样保留；官方 versionCode。

  2. 系统/管理器里会看到那个残留条目（你说的"多一个 read 安装包"）。

清理办法（已执行）：

清理后 7.3.6 一次装成功。

如何避免：卸载时不要用"删除并保留数据"的方式（MT管理器 卸载若提供该选项就不要勾），
或者直接让我用 pm uninstall 来卸；需要保数据时用同签名的升级覆盖（pm install -r）而不是卸载重装。

17. 决定性实验 T1：签名就是触发器 —— 干净包改造路线的终点

17.1 实验设计（把变量压到只剩一个）

包内容改动签名
原包 红果免费短剧V7.3.7.apk—渠道证书 CN=novel, O=fq, L=sz (SHA1 73:CD:22:A6:…)
T1 红果V7.3.7_对照T1_只换签名.apk0 处（23,109 个条目逐条 MD5 比对，差异 0）我的证书 CN=DSH Sandbox

T1 实测结果：与原包完全相同的报错（弹"当前版本不安全，请到正规应用市场下载" + 剧场"网络出错，请点击重试"）。

17.2 结论

  1. 触发点是签名本身，与 dex 是否被修改无关；
  2. 校验发生在原生安全层（libmetasec_ml.so 这类）与服务端，Java 层没有：
    1. 全 App 扫描"读签名/证书"的类，命中的全是第三方 SDK —— 支付宝(s7/r,b7/b)、欧珀 OUID(j6/c)、华为 HMS(qp8/a)、androidx(PackageInfoCompat)；
    2. 没有任何一处是 App 自己的校验逻辑（也就是说 smali 层无处可改）。
  3. ⇒ 干净包 + 重签名 = 必死。想在 dex 里"改了就完事"是不可能的。

17.3 那渠道魔改包为什么能用？

因为它拖着一个原生壳 libseccore.so（SONAME 是随机 UUID、读 /proc/self/maps 自保护）——
这个壳的职责就是绕过签名/完整性校验（T1 证明了没有它必死）。
它同时还在做更新弹窗、设备指纹采集等事。

17.4 由此确定的可行路线（唯一）

底座能否改造后可用说明
渠道魔改包✓ 可以保留它的原生壳 + 只做"去弹窗/官方版本号"这类改动
干净原始包✗ 不可以任何重签名都触发风控（T1 已证）

代价：libseccore.so 是 ARM64-only，x86 模拟器（雷电/MuMu）只能靠 ARM 转译执行它 → 壳自检失败 → 闪退。
⇒ x86 模拟器上无解；真机 / VMOS（ARM）可用。

17.5 文档记录：干净包方案的产物

  • 红果免费短剧V7.3.7_去广告去升级会员版.apk：在干净包上打了 34 处补丁（去升级 17 + 会员 13 + 去广告 6）， 类集合零丢失、签名 v1+v2+v3 —— 但受 T1 结论限制，实际不可用，仅作为补丁清单/思路留档：

18.1 两个对称实验的对照

⇒ 结论：能否正常联网，取决于"包里有没有魔改的原生壳"，与签名是谁签的无关。

18.2 机理

  • 干净包：无壳 → 服务端/原生安全层的校验通过不了 → 返回错误码 110 → NetReqUtil 里 if (错误码 == 0x6e) assertIllegalAccess() 命中 → 弹提示 + 内容接口被掐（T1 证实）。
  • 魔改包：lib/arm64-v8a/libseccore.so（随机 UUID SONAME、读 /proc/self/maps 的商业加固壳） 职责就是绕过签名/完整性校验 → 即使我重新签名，壳照样把校验兜住 ✓

18.3 最终路线

底座 = 渠道魔改包（必须保留壳）+ 只做"去弹窗 / 官方版本号"这类最小改动

② MainFragmentActivity 里 а.A(...) 的更新 URL 换成死地址（壳仍加载，但拿不到数据 → 不弹）

18.4 唯一未解的环境限制

libseccore.so 是 ARM64-only：

环境结果

⇒ x86 模拟器上无解：带壳必崩，不带壳必断网。这一点已用实验闭环，不再猜测。

19. 最终可用配方 + 工具包 v2（已实验闭环）

19.1 最终结论（一句话）

**以渠道魔改包为底座，只做三类最小改动：App 自身升级链路置空、assertIllegalAccess 置空、
把魔改的两个域名换成死地址。** 壳与载荷一律保留 ⇒ 弹窗不再来 + 联网正常 + 会员/去广告能力保留。

19.3 为什么是"死地址"而不是"摘钩子"

  • 摘钩子 = 模块不加载 = 壳不生效 = 断网（T1 对照）
  • 改死地址 = 模块照常加载（壳生效）+ 拿不到弹窗数据 = 两全 ✓
  • 弹窗显示动作在 native（resolveAndShowAsync/showFragmentInternal），Java 层无调用点， 所以"只掐显示"在 dex 层做不到 —— 这是把 DialogFragment.show、Glide com/dT、 androidx com/hX 全部排除后的结论。
