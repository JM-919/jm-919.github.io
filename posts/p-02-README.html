5. 激活码 (Activation Code) 流程

应用内的另一条路径 (MZActivationController):

官方请求体用 HTTP_ENC (1024 bit) 加密, 私钥不在样本中, 因此无法解密官方请求,<br>也就无法做到"对官方客户端完全透明"的服务端替换。本实现提供两种等价接口:

  • POST /api/activate (JSON) —— 明文参数, 语义与官方一致
  • POST /cgi-bin/suite_exp.cgi —— 与官方同名的表单/明文接口, 返回 status/name/regcode/regtype

两者都由同一套 120 bit 私钥签发注册码, 结果与官方注册码在应用侧等价。

5.5 第三种凭证: 激活码 (Activation Code) —— 纯校验字符, 无签名

WzReg::IsActivationCode(char*) WzEngine 0xf766e@:

  • cb32 (__ZL4cb32 0x2bf860) = 0123456789ACDEFGHJKLMNPQRTUVWXYZ@ (32 字符, 无 B/I/O/S)
  • cd32 (__ZL4cd32 @ 0x2e3150) = 256 字节查表: 字符 -> 0..31, 非法 = 0xff; 字符 = 在表中值为 32; 小写 / 空格 / B I O S 均为 0xff
  • 本仓库 winzip_actcode.py 的 CD32 与二进制 逐字节一致(ASCII 段全等), 已自检

=> 激活码可以本地批量生成: python3 winzip_actcode.py 5<br>(输出形如 DXKEX-44895-PF5HN-N3CUF, 5-5-5-5 分组显示)

激活码怎么用 (客户端流程, 0x100140805 / 0x100140b6f)

两点含义:

  1. 激活码本身只是 兑换券 —— 应用侧不会本地换出注册码, 必须联网;
  2. 请求体私钥不可得 => 服务端解不开请求; 但响应体就是客户端拿去自校验的注册码, 而校验用的名字是用户在对话框里自己填的 —— 所以固定一个服务名就能闭环。

本仓库 license_server.py 已实现这三个端点:

端点作用
GET /getActLoc.cgi下发自己的激活服务地址 (配合 hosts 把 www.winzip.com 指到本机)
POST /activate.cgi (任意路径, 二进制体)忽略加密体, 直接回 --service-name 的注册码纯文本
GET /api/actcode?count=N批量生成激活码
POST /api/actcode/verify校验激活码

用法: python3 license_server.py --service-name BS, 客户端激活窗口里把<br>Registered to Name 也填成 BS, 点激活即可拿到 PRO 注册码。

8. 结论 / 边界

  • 单用户注册码的签名密钥是 120 bit RSA, 已分解, 因此可以为任意注册名签发被应用接受的 注册码 —— 授权服务程序 (license_server.py) 即建立在此之上。
  • 校验位检查是"单边"的 (见 3.2 第 3 步), 把第 25 个字符取全 1 也能通过; 本实现仍输出规范校验位。
  • 激活请求体用 1024 bit HTTP_ENC 加密, 私钥不在样本内, 故服务端采用明文等价协议; 应用侧调用的是同一套注册码签发算法, 结果等价。
  • 多用户 MUL 路径依赖 1024 bit MU_PK, 不可伪造, 未实现。
