奥维互动地图 VIP/SVIP 完美版 —— 完整补丁文档

作者 ZY· 2026-09-21· 补丁改造· 12796 字· 约 27 分钟
#补丁改造#Android
目标：不依赖服务器、不改数据库，把「VIP/SVIP 身份、对象(收藏)数量、地图水印、
升级提示、VIP管理页显示」这一整套本地门禁在 Java 层 + native 层 同时打开。

1. 样本与产物

2. 授权体系速览（为什么两处都要动）

  • Java 层：com.ovital.ovitalMap.JNIOMapSrv 里一组 public static native 是壳， 全应用 60+ 处判 VIP 都调它们（形如 if(!IsVip()){弹“需要VIP…”;return;}）。
  • native 层：真正干活的是 libovitalMap.so 里的 OMapSrv::*； 地图绘制、对象数量限制、DXF 导出、等高线 这些不走 Java，必须改 so。
  • 两者是「与」关系：只改 Java = 界面像 VIP、功能还是残废；只改 so = 功能开了、界面仍提示要买。

3. Java 层补丁（5 处）

3.1 JNIOMapSrv —— 10 个 native 壳改成 Java 桩

方法签名桩体

为什么是 6 而不是 GetMaxVipLevel()：
GetMaxVipLevel()（JNIODef，native，反汇编 = mov w0,#0xa; ret）返回 10，是开区间上界。
qc.v(I) 里 0<level<10 才映射成名字，>=10 直接落 "普通版"；
而「(SVIP)」相关分支全部按 等级 == 6 精确命中（UserTrackSetActivity 用 6 取限额并配 %s(SVIP)；
MacVipUpgradeActivity 的 Ib;->b("SVIP",6)；ProManageActivity 用 >5 判定 SVIP）。
填 10 = SVIP 显示消失，填 6 才对。

3.2 ovitalMapActivity.r() —— 去掉“发现新版本/请到应用市场中升级新版本”弹窗

在该 handler 的 what == 0x34 分支里，删掉结尾那一行

（D7 是弹窗构造器；删掉后直接走到 return-void）。其余 what 分支不动。

5. 打包与签名（踩过的坑）

  1. 必须 v1+v2+v3 全签：只 v2 在部分 ROM 上装不上/起不来。
  2. resources.arsc 必须 STORED + 4 字节对齐（targetSdk≥30 平台强制）， 改包时不要动它的存储方式与偏移（lib/repack.py 只追加尾部条目 + 重写中央目录，正好满足）。
  3. 签名密钥：noupdate.keystore（PKCS12，alias/pass 都是 noupdate/123456）。 奥维容忍重签（同内容重签实测可正常运行），不像某些壳有强校验。
  4. versionCode 若非要改，别用夸张值（如 999999999 会被 native 自检判定异常、启动 8 秒后静默退出）； 用正常递增（如 1072020 → 1073000）即可。
  5. repack.py 回填后 APK 会变大（旧条目变成垃圾），签名的 zipalign 会顺手清掉， 所以不要用 --skipZipAlign。

8. 已知边界（改包改不到的）

  1. 服务器侧：买 VIP、绑定设备数、云空间额度、企业云收藏夹 —— 按账号在服务端校验，改包无效。
  2. GetOviObjCntLimit（只是显示“对象上限 N”的数字）未改，避免像 GetVipLevelLimitCount 那样返回超大值触发崩溃；实际已不拦截。
  3. GetLastSignPicVipType 直接读实例字段（ldr w0,[x0,#0x2F0xxx]），不是能简单改返回值的函数； 要动得改整个 SetVipLevel 写入路径，风险高，未做。
  4. OMapSrv::SelfCheckVip / SetTmpVipLevel 属引擎内部自检，已被 IsVip* 覆盖，未单独改。

9. 「装了模组版，卸载后原版装不上，提示有残留」——真因与一次解决

真因（两条，都不是文件，所以文件管理器里永远找不到）

系统卸载（桌面长按→卸载）在国产 ROM 上默认是 DELETE_KEEP_DATA（卸载保留数据）。
保留下来的东西是绑定签名和版本号的：

情况系统报错安装器文案
保留的数据属于模组版签名，再装官方原版（签名不同）INSTALL_FAILED_UPDATE_INCOMPATIBLE: signatures do not match「存在残留数据」
保留记录里记着上次的 versionCode（如模组版 1073000），再装更低的官方（1072020）INSTALL_FAILED_VERSION_DOWNGRADE: Downgrade detected on app uninstalled with DELETE_KEEP_DATA「存在残留数据」

两条都在本机实测复现过。adb install -d（允许降级）也过不去，别指望它。

一次解决

核心动作：卸载时连数据一起删。

  • 手机：设置→应用→应用管理→奥维互动地图→存储→清除数据→返回→卸载； 或长按图标→ⓘ应用信息→存储→清除数据→再卸载。
  • adb（推荐，最干净）：
  • 一键脚本：bash 奥维一键补丁/装机清理.sh [要装的APK] —— 遍历所有用户（含分身 user 128）连着数据卸载 → 清未完成安装会话 → 清 /sdcard/Android/{data,media,obb}/<包名> → 装目标包。

不再复发（根治）

模组包的 versionCode 必须 == 官方包（我们已按此重做）。
另外 versionCode 与 versionName 必须互相自洽——本机实测把官方 10.7.2 的
versionCode=1072020 配上 versionName=10.7.3.35899，引擎会在启动 16 秒后静默退出。
所以最终成品是直接拿官方 APK 打补丁得到的：versionCode=1072020、versionName=10.7.2.35899，
完全保持官方数值，只换 dex 与 so。

为什么要卸载才能换包：模组版与原版签名不同（拿不到 Ovital 私钥），签名相同才能覆盖安装。
想做到「原版/模组版共存、互不干扰」只能改包名，代价是数据不共享且要改全部组件/权限名，风险高。

10. 换版本必看：官方会改混淆名（10.7.3.36288 实测差异）

同一套逻辑，官方在两个版本里用了不同的混淆名，所以补丁脚本必须按结构/签名匹配，
不能写死类名或方法名。lib/ 下的脚本已全部按此改造：

补丁点10.7.210.7.3.36288脚本怎么定位
设置 TextView 文本的 helperLcom/ovital/ovitalMap/Mz;->A(TextView,String)ILcom/ovital/ovitalMap/cA;->A(TextView,String)I从被替换的那段原文里正则抓出 L(.*);->A(Landroid/widget/TextView;Ljava/lang/String;)I，原样复用
升级弹窗构造函数oFun;->D7(Context,String,String,OnClickListener,String,OnClickListener,String)Lt4;oFun;->E7(...)（签名完全一样）按完整方法签名匹配，不按方法名
JNIOMapSrv 的 10 个 native 壳同名同名按 .method public static native <签名> 文本
好友上限调用点同名同名按 const/4 vX, -0x1 + GetVipLevelLimit(II)I 文本
19 处 native地址如 0x3f66a44地址全变，如 0x3f6fba8按 ELF 符号名（_ZN7OMapSrv11GetVipLevelEv）

踩过的坑（务必记住）：如果 helper 类抓错/写死，会得到一个引用了不存在的方法的 dex，
表现就是 —— VIP管理页一点就闪退、什么都不显示（NoSuchMethodError）。
10.7.3.36288 上就是这么翻的车；现已修正并实测正常。

换新版本时的自检：一键补丁.sh 跑完看输出，5 条 Java 补丁 + 19 条 native 补丁都应为 [OK]，
出现 [跳过] 就说明官方改了结构，需要更新 lib/dex_patch.py 的匹配串。

11. VIP管理页 4 行的取值规则（显示层实现，不落盘）

行取值说明
绑定的VIP用户dshVip.a(ctx)5~8 位"随机"码，由 Settings.Secure.ANDROID_ID 的 hashCode 取模派生：abs(hashCode)%90000000+10000000
VIP类型固定 SVIP直接写死字符串
到期时间dshVip.b(ctx)PackageInfo.firstInstallTime + 10 年 → yyyy-MM-dd
最后一次升级时间dshVip.c(ctx)PackageInfo.firstInstallTime → yyyy-MM-dd

为什么用 ANDROID_ID 派生，而不是写文件：

  • 纯显示层，不落任何盘、不改数据、不申请权限；
  • ANDROID_ID 由「设备 + 签名密钥 + 用户」三者决定，同一台机、同一个签名，卸载重装后不变 —— 正好满足"第一次随机、以后都按第一次算"；
  • 不同设备算出来不同，看着像真的账号 ID，不虚假。

实测（10.7.3.36288，本机）：首次显示 87676467（8 位）；
adb uninstall 连数据卸载后重装，再进 VIP管理 —— 仍然是 87676467。

注意：adb shell settings get secure android_id 拿到的是 shell 自己的 ANDROID_ID，
和 APP 进程里读到的不是同一个值，所以别拿它去对答案。

12. 会员等级 = 9（最高），显示仍为 SVIP —— 以及踩过的两个坑

等级取值

JNIODef.GetMaxVipLevel()（native）= mov w0,#0xa; ret → 10，是开区间上界；
qc.v(I) 里只有 0 < level < 10 才映射成名字。所以合法等级是 1~9，最高 9。

最终配置：

位置值
Java JNIOMapSrv.GetVipLevel() / GetMiVipLevel()9
native OMapSrv::GetVipLevel() / GetVipLevelInt()9
native OMapSrv::IsVip9SpecUser()0（见下）
Java JNIOCommon.GetVipTypeName(IIZ) / GetVipLevelName(I)换成桩：等级 ≥6 一律返回 SVIP，其余返回 VIP<等级>

坑 1：等级 9 会弹「当前设备所绑定的VIP9处于失效状态，请联网验证」

因为 VIP9 在引擎里是特殊用户档（OMapSrv::IsVip9SpecUser），需要服务器侧登记。
把 IsVip9SpecUser 打成 0（我们不是 VIP9 特殊用户）后，这个失效提示就消失了。

坑 2：const/4 装不下 9

const/4 v0, 0x9 是非法字节码（const/4 只吃 -8~7），smali 会报
Invalid literal value: 9. Must be between -8 and 7。等级桩必须写 const/16 v0, 0x9。
（一键补丁.sh 已改成回编译后检查 classes2.dex 是否真的生成，失败立即退出，
免得像之前那样默默失败、最后签名出一个半成品。）

为什么不直接用等级 6

等级 6 恰好是 native 名字表里的 SVIP，但只有 6；要"最高等级"就得上 9。
上 9 之后 native 名字函数会返回 VIP9，所以把 JNIOCommon 的两个名字函数换成桩，
让等级 ≥6 统一显示 SVIP —— 既拿到最高等级的全部权限，界面上又还是 SVIP。

实测（10.7.3.36288）：更多页头部 當前版本: V10.7.3.36288(64 Bits) SVIP；
VIP管理页四行正常、无失效提示、无闪退。

14. 升级成功后的收尾：清旧版，只留新版

规则：新版本打包装机验收通过后，立刻清掉旧版，工作目录只保留新版。

清理范围：OvitVIP_Perfect_*.apk、omapAndroidV*.apk、omapAndroid*.apk、奧維互動地圖_*.apk。
不碰：文档、工具包、keystore、其它 App 的包。

三重保险（血泪教训）：

  1. 默认只预演，必须显式加 --yes 才真删；
  2. 硬闸：任何文件只要版本号 == 本系列最高版本，一律不删 —— 绝不可能把新版删掉；
  3. 指定的保留文件不存在 → 直接中止。
为什么要有硬闸：早期版本按"修改时间最新"挑保留项，两个包修改时间在同一秒时挑错了，
把新版删了（成品可以从一键补丁重打，但如果同时把官方原始包删了就真的没了）。
所以现在改成按版本号比较 + 硬闸 + 默认预演。
